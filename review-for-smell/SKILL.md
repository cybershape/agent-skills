# 代码坏味道审查（review-for-smell）

你是**审查者**，不是修复者。本 skill 的目标是**找出坏味道并准确定位**，给出修复建议；默认不直接改代码（用户明确要求时才改）。

**输出语言**：报告与说明用**中文**。

**诚实边界**：

- 坏味道是**启发式信号**，不是错误。同一段代码在不同的上下文里可能是合理设计；报告里区分「确定问题」与「疑似，需人工确认」。
- 静态审查抓不到运行时行为（性能、时序、并发）。涉及这些的 smell 标为「需运行时验证」。
- 发现 smell 后**不要顺手改代码**，除非用户明确要求；改之前先与用户确认范围。

---

## 触发方式

用户可能说：「review for smell」「扫一下坏味道」「检查代码质量」「这个文件有什么问题」等。

参数解析（未给则用默认）：

| 参数 | 默认 | 说明 |
|------|------|------|
| `scope` | 自上次审查以来的变更（git diff） | 可指定：路径、文件、目录、或「全部」 |
| `since` | 最近一次 review 的 tag / 上次审查基线；没有则问用户或全量 | 变更基线 |
| `severity` | 全部 | 只报告某级以上（blocker / high / medium / low） |
| `fix` | 否 | 是否同时修复（默认只报告） |

示例：「review-for-smell scope=Quickest/Automation」「review-for-smell scope=src/ since=上次发布 tag fix=yes」

---

## Phase 1 — 定范围

1. 解析 `scope` / `since`。
2. 若 `scope` 未指定且存在 git 仓库：用 `git diff` 或 `git log` 找出最近变更文件；变更过大（> 800 行）时按目录/模块切片，逐片审查，不要一次扫全仓库然后只给泛泛结论。
3. 向用户报告范围：文件数、变更行数、切片计划（如有）。

## Phase 2 — 机械扫描（可快速定位的 smell）

按文件逐个过，命中即记录（文件:行号）。这一 phase 可以不读完整文件，靠 grep / regex 预筛再确认。

### P2.1 魔法数字与硬编码

- 裸数字字面量（`sleep(3000)`、`x + 42`、`width * 2`），尤其无注释、无常量名
- 硬编码路径 / URL / 密钥 / 端口 / 超时秒数
- 例外：`0`、`1`、`-1`、`100%` 等自解释边界值不算

### P2.2 重复

- 相同代码块出现 ≥ 2 处（复制粘贴）
- 相同字符串 / 字面量散落多处
- 相同的前置判断序列（`if null → default → 处理`）重复出现

### P2.3 死代码与历史包袱

- 注释掉的代码块
- 无人调用的方法 / 字段 / using / import
- 永远 false / true 的分支（`if (x == x)`、`if (false)`）
- 只写不读的赋值、从未变更的「可变」字段

### P2.4 异常与错误处理

- 空 `catch {}` / 吞异常
- `catch (Exception e)` 后只打日志不处理、不重抛
- 用异常做流程控制（try/catch 当 if 用）
- catch 后返回 null 掩盖失败原因

### P2.5 注释

- 注释解释「怎么做」而非「为什么」（代码本身该自解释）
- 整段复制代码 + 注释「此处与 XX 相同」（本质是重复）
- 过期注释（注释与代码行为矛盾）

### P2.6 工程硬规则（按项目可选启用）

- 项目约束的禁止项（例如：禁止 `Debug.WriteLine`、禁止固定 `Sleep`、像素常量必须入 `DpiContext`）
- 若项目有 AGENTS.md / 文档中的硬规则，在本 phase 对照执行

## Phase 3 — 语义分析（需读代码判断的 smell）

对 Phase 2 未覆盖的文件或关键文件通读，按以下维度判断。每条结论都要给出**依据**，不只是「感觉」。

### P3.1 函数级别

- **长函数**：超过一屏 / 职责超过一件（一个方法里既校验又转换又落库又发通知）
- **过长参数列表**：> 4 个参数，或成组参数反复出现（见数据泥团）
- **输出参数**：用 ref / out / 指针偷返回值，应返回结果对象
- **标志参数**：`process(verbose=true)` 暗示应拆两个方法；`type == "A"` 分支链暗示多态/策略/字典
- **过深嵌套**：if/for/while 嵌套 > 3 层，缺 guard clause（早返回）

### P3.2 类与结构

- **上帝对象**：一个类包揽 N 种不相关职责（既是模型又是服务又是配置）
- **中间人**：方法只转发给另一个对象，无附加逻辑；转发链过长
- **特性依恋**：方法大量使用别的对象的数据/方法，自己的字段很少用
- **数据类**：只有 getter/setter 没有行为，行为散落在外部（注意：纯 DTO 不算）
- **依恋情结（Shotgun Surgery）**：改一个需求要动很多文件
- **发散式变化（Divergent Change）**：一个类因多个不相关原因被修改

### P3.3 数据与状态

- **数据泥团**：`(x, y, width, height)`、`(start, end, step)` 等成组出现 ≥ 3 处，应封装
- **裸游荡数据**：全局可变状态、静态可变字段、单例堆状态，难以测试
- **空值泛滥**：到处判 null / 返回 null 表示「没有」，考虑 Optional / 空对象
- **可变性过度**：能 immutable 的字段有 setter；被外部随意改写

### P3.4 时序与生命周期

- **隐性时序依赖**：`Init()` / `Connect()` 必须按特定顺序调用，调用者不知道
- **资源泄漏嫌疑**：打开的文件 / 流 / 句柄 / 连接没有配对关闭（`using` / `defer` / `finally`）
- **对象生命周期混乱**：事件订阅未取消、缓存无限增长

### P3.5 命名与可读性

- 误导性命名：`data`、`temp`、`tmp`、`flag`、`handle`
- 名字与行为不符（`IsValid()` 里做了删除）
- 名词堆砌的过度标识符（`ManagerProviderHandlerFactory` 这类）
- 含义需要翻上下文才能懂的缩写

## Phase 4 — 汇总报告

输出结构化报告，按严重度分级：

```
### 审查范围
路径 / 基线 / 文件数 / 变更行数

### 严重度定义
- blocker：会导致 bug 或违反项目硬规则的 smell（如吞异常掩盖真实错误、魔法数字踩到项目硬约束）
- high：大概率引发维护问题的（如重复代码、深层嵌套、特性依恋）
- medium：有争议但值得改的（如长参数列表、命名不佳）
- low：风格类，可批量处理（如注释掉的代码、轻微魔法数字）

### 发现清单（按严重度）
| # | 严重度 | 位置 | 类别 | 描述 | 建议 | 确定/疑似 |
|---|--------|------|------|------|------|-----------|
| 1 | high | src/a.cs:42 | 空捕获 | 吞掉 IO 异常，失败不可见 | 记录日志并返回失败结果 | 确定 |

### 类别统计
魔法数字 n 处 / 重复 n 处 / 空捕获 n 处 / ...

### 修复优先级建议
按「先 blocker/high，再批量 low」排序；高风险改动（重构类结构）建议单独任务做，不要夹带。
```

## Phase 5 — 修复（可选）

仅当用户 `fix=yes` 或明确要求时才执行：

1. 先报告发现清单并**等待用户确认修复范围**（哪些条目修、哪些不修）。
2. 修复时一次只改一个类别，保持行为不变；机械类（魔法数字提常量、删死代码）可以直接改，结构类（拆函数、提取类）先说明影响面。
3. 改完重新跑扫描确认没有引入新 smell；有测试的项目提醒用户跑测试。
4. 报告「已修复 / 跳过 / 需人工确认」清单。

---

## 项目特定规则挂载

若项目有 AGENTS.md 或 Docs 中的硬约束（如「像素常量只进 DpiContext」「禁止固定 Sleep」「失败必须走结构化错误码」），在 Phase 2.6 对照执行；项目无此类规则时跳过该条，**不要**凭空套用别的项目的约束。

## 反模式（本 skill 自身禁止）

- 禁止「扫一眼就下结论」：机械 phase 必须给出文件:行号。
- 禁止把 smell 当 bug 报告：用「建议」「疑似」措辞，除非能证明会出错。
- 禁止一次报告超过 ~30 条：超过说明范围太大，先切片再报，避免淹没重点。
- 禁止未经确认就大改代码：先出报告，等用户拍板。
